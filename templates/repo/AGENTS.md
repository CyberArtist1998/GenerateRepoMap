# Operating rules

## 1. Placeholders are not values

If any `<...>` placeholder above is still unfilled, or a command you need is
marked `UNVERIFIED` or `FAILED` in FACTS.md, **stop and ask**. Do not infer it,
do not guess a likely value, do not substitute a convention.

An unfilled placeholder is worse than a missing file: a missing file makes you
ask, an unfilled one invites you to invent.

## 2. Tool preference order

Use the cheapest tool that answers the question. Do not skip down the list.

1. `.agent/ARCHITECTURE.md` — who imports what. Already computed; read it first.
2. `rg` — exact text. `-w` for identifiers, `-t <lang>` to scope, `-n` for lines.
3. `ast-grep` — code shape, when text matching is too noisy.
4. Typechecker / LSP — definitions and references, when you need certainty.
5. `git log -S "<term>"` — when you need to know why or when something appeared.
6. Run the code — when static analysis is inconclusive.

Never `cat` a file to search it. Never read a whole file when a range suffices.

## 3. State lives on disk, not in this conversation

Before any read, check `.agent/done.txt`. After any read, append to it.

```
.agent/worklist.txt    # pending units, one per line
.agent/done.txt        # completed units
.agent/findings.md     # located items, file:line, one per line
.agent/questions.md    # your escalations
.agent/decisions.md    # human answers (read-only for you)
```

**Create any of these that do not exist.** Their absence is the normal starting
state, not an error.

Re-read `.agent/decisions.md` at session start and again before you report.
Answers may have been added since you last looked.

Never keep an important result only in your reply. Write it to a file first.

## 4. Locate before you change

Do not edit anything until `.agent/findings.md` is complete.

1. Read `ARCHITECTURE.md` — it names the entry points and the core files.
2. Broad sweep with guessed vocabulary.
3. Open the top 3 hits. Extract the **project's actual identifiers**.
4. Re-sweep on those real identifiers.
5. Find each identifier's definition, then all its references.
6. Stop only when the closure condition is met (rule 7).

Files marked `PLUGIN` or `RUNTIME-LOADED` in ARCHITECTURE.md are reached by name
at runtime, not by import. Text search will find them; a reference search will
not. Do not conclude they are unused.

## 5. Minimal diff — strict order

1. Change the **definition**. One line if possible.
2. Change the **config or data**.
3. Change the **call sites**.
4. **Delete** code.

Do not use rung 3 until rungs 1 and 2 are proven impossible. Do not use rung 4
without explicit human approval.

**State which rung you are on before every edit.**

Prefer edits to files ARCHITECTURE.md marks `LEAF`. A change to a file marked
`CORE` has the blast radius shown in its "imported by" count — say that count
out loud before editing one.

## 6. One unit at a time

One file per task. After each file, run the typecheck or build command from
FACTS.md, then commit.

If the check fails, revert that file and retry smaller. **`git checkout -- <file>`
permanently discards your uncommitted work on it** — if the edit was expensive,
save a copy first.

**Exception:** when a change cannot compile without a companion edit (a rename,
a signature change, a moved symbol), commit the smallest set that compiles
together and say in your report why it was more than one file. Do not split a
change into commits that are individually broken.

Edit bottom-up: leaves → services → config. Removing a definition before its
usages guarantees a broken intermediate state.

## 7. Stopping

You are done only when an **oracle** says so:

- the verification sweep returns zero hits, **and**
- the build or typecheck from FACTS.md is green, **and**
- the test suite has been run and each failure classified.

"I have not found anything new" is not a stopping condition. "The worklist is
empty" is valid only if the worklist was provably complete.

If FACTS.md lists no VERIFIED command, there is no oracle. Say so plainly and
hand the closure decision back to the human.

## 8. Ambiguity — escalate, do not guess

A hit counts only if it sits inside a control-flow guard (`if`, `&&`, `?:`, `?.`,
early return) or a configuration collection. A hit inside a string literal,
comment, or data-formatting expression does not count.

If you cannot classify a hit, append to `.agent/questions.md`:

```
## <file>:<line>
<3 lines of surrounding code>
Q: <the specific question>
```

Then **continue with the items you are certain about. Do not block.** Questions
are answered in batches; stopping on each one makes the process unusable.

## 9. Never

- Never install a package without confirming it exists
  (`npm view <pkg>` / `pip index versions <pkg>`). If unverifiable, stop.
- Never install into the system interpreter. Use the path in FACTS.md.
- Never `--force-reinstall` or `--upgrade` against a system-wide interpreter.
- Never invent a file path, function name, or command. If you have not read it,
  say so.
- Never assume a green build means correct behaviour. State what still needs
  manual verification.
- Never modify generated or dependency directories.
- Never rewrite git history, force-push, or amend commits you did not create.
- Never run `rm -rf`, `git clean -fdx`, or `git reset --hard`. Each destroys
  uncommitted work with no recovery. If you believe one is needed, ask.

## 10. Report format

End every task with exactly this block:

```
CHANGED:    <files, one per line>
RUNG:       <which minimal-diff rung each edit used>
COMMITS:    <hashes, or none>
BUILD:      pass | fail | not run
TESTS:      <n passed, n failed — and whether failures were expected>
UNVERIFIED: <what a human still needs to check by hand>
QUESTIONS:  <count in questions.md>
```

`UNVERIFIED` is the most important line. A green build cannot cover runtime
behaviour, dynamic dispatch, or anything reached only through a plugin loader.
Never leave it empty — if you genuinely believe nothing is unverified, write
that and say why.
